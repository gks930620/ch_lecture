## 공공데이터API, CORS 정리.md

### [높음] 112-115행 — Simple Request 조건이 정반대로 서술됨 (검수자 직접 재확인 완료)
- 제목은 "preflght 없이 Simple Request 보내는 조건"인데 나열 내용(PUT/DELETE/PATCH 등 "GET/POST/HEAD가 아닌 것", 임의 헤더 포함, Content-Type이 세 가지가 "아닌 경우")은 전부 **preflight가 발생하는 조건**임. 초보자가 그대로 읽으면 거꾸로 암기하게 됨.
- **수정 제안**: 제목을 "Preflight가 발생하는 조건"으로 바꾸거나, 내용을 Simple Request 조건(GET/POST/HEAD **인** 경우, 커스텀 헤더 없음, Content-Type이 세 가지 중 하나**인** 경우)으로 뒤집기. "preflght" 오타(→ preflight)도 수정.

### [중간] 12행 — RestTemplate "⚠️ Deprecated" 표기는 부정확
- RestTemplate은 deprecated가 아니라 **유지보수 모드(maintenance mode)**. 실제 코드 ApiProxyController.java:29 주석에는 정확히 적혀 있어 문서와 코드 주석이 서로 모순.
- **수정 제안**: "유지보수 모드(신규 기능 없음)"로 수정.

### [낮음] 150행 — "CSRF 설정을 하면 ... 403"의 주체 불명
- CSRF 토큰 검증은 Spring Security 기능인데 이 프로젝트는 Security 미사용. "Spring Security의 CSRF 보호 기능을 켜면"으로 주체 명시 + 이 프로젝트 미적용 안내.

### [낮음] 78, 142, 46행 — 오타: "COSR"→CORS, "믿을만한 오리지만"→"오리진만", "a\<img\>나"→"`<img>`나"

## 서비스설계_정리.md

### [중간] 66-79행 — 문서가 "❌ 위험"이라 경고하는 패턴을 실제 프로젝트 코드가 그대로 사용
- 문서는 "Controller에서 여러 Service 직접 호출 → 중간 실패 시 롤백 안 됨"을 위험 사례로 제시하는데, 실제 CommunityController.delete()(187-201행)가 정확히 이 구조: `fileService.detachFilesByRefId()` → `commentService.deleteCommentsByCommunityId()` → `communityService.deleteCommunity()`를 트랜잭션 없이 순차 호출. 특히 **권한 체크가 마지막 deleteCommunity() 안에서 수행**되어, 작성자가 아닌 사용자가 삭제 시도하면 파일 고아 처리·댓글 하드 삭제가 이미 실행된 뒤 403 발생 — 문서의 경고 시나리오가 실제로 재현되는 코드 버그 성격.
- **수정 제안**: 문서에 "이 프로젝트의 delete 흐름이 바로 이 한계 사례이며, 개선하려면 Facade + @Transactional로 묶고 권한 체크를 맨 앞으로" 연결 설명 추가. **코드 자체 수정도 검토 대상 (작업자 확인 필요).**

- (참고) Facade @Transactional 설명, Controller↔Facade 1:1 / Facade↔DomainService N:M 등 개념 설명은 정확. 189행 단서 덕에 프로젝트_구조_정리와도 정합.
