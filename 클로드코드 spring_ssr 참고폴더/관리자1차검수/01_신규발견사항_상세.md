## 중간 (배포 전 조치 권고)

### M1. 파일 업로드 API 무인증 + 문서의 "자체 인증" 오표기

- **소스**: `spring_ssr/src/main/java/com/ch/basic/file/controller/FileApiController.java` — `uploadFiles()`(POST `/api/files/upload`), `getFiles()`(GET `/api/files`)
- **문서**: `docs/spring_ssr/프로젝트_구조_정리.md:47` — 적용 범위 표의 `/api/**` (댓글 API - 자체 인증) 행
- **문제**:
  - `FileApiController`에는 `HttpSession`/세션 체크 코드가 **한 줄도 없음** (관리자 grep 직접 확인 — session 관련 매치 0건). LoginCheckInterceptor의 include 4개 패턴에도 미포함. 즉 비로그인 사용자가 `POST /api/files/upload`로 임의 바이너리를 무제한 업로드 가능. 고아 정리 스케줄러는 24시간 유예 + refId=0 대상만 삭제하므로 그 사이 디스크 적재가 성립.
  - 동일하게 `ApiProxyController`도 세션 체크 없음.
  - 그런데 문서 표는 `/api/**` 전체를 "자체 인증" 항목으로 묶어 표기 → 초보자는 "모든 API는 자체 인증된다"고 배우게 됨. 실제로 자체 인증하는 것은 **댓글 API(CommentApiController)의 쓰기 계열뿐**.
- **유형**: 2차검수 높음 1번(WebConfig exclude — "문서가 잘못된 동작을 정상으로 공식화")과 동일 유형. 소스 결함 + 문서 공식화가 결합된 케이스라 중간으로 판정 (강의용 로컬 프로젝트임을 감안해 높음은 아님).
- **수정 제안** (둘 중 하나, 병행 권장):
  1. 소스: `uploadFiles()`에 `HttpSession` 파라미터를 받아 댓글 API와 동일하게 로그인 체크 후 401 JSON 반환 (WebConfig 주석 67-70행이 이미 안내하는 "ApiLoginCheckInterceptor 분리" 방향과도 일치)
  2. 문서: 표 각주를 "댓글 API 쓰기 계열만 자체 인증. 파일/프록시 API는 현재 인증 없음(강의 단순화 — 실무에서는 API용 Interceptor 필요)"로 정정

### M2. 게시글 본문 `th:utext` 저장형 XSS (서버측 새니타이즈 부재)

- **위치**: `spring_ssr/src/main/resources/templates/community/detail.html:151` — `th:utext="${community.content}"`
- **문제**: 본문은 Quill 에디터 HTML을 가공 없이 저장하고(`CommunityService`에 정화 로직 없음, 프로젝트 전체에 jsoup/sanitizer 의존성 없음 — 관리자 grep 직접 확인) 화면에서 `th:utext`로 이스케이프 없이 렌더링. `POST /community/write`에 `<img src=x onerror=...>` 류를 직접 넣으면 저장형 XSS 성립. 같은 화면의 **댓글은 JS `escapeHtml`로 방어**하고 있어 방어 정책이 비대칭 — 초보자가 "왜 댓글만?"이라는 잘못된 기준을 배울 수 있음.
- **수정 제안**: 강의 범위상 소스 수정이 부담이면 최소한 문서(프로젝트_구조 또는 개념_02)에 "본문 HTML은 신뢰된 입력 가정 — 실서비스는 서버측 화이트리스트 새니타이즈(jsoup 등) 필수"를 명시. 여력이 되면 저장 시 정화 추가.

### M3. `LoginCheckInterceptor.java:23-24` Javadoc — 삭제된 exclude 설정을 사실처럼 서술

- **위치**: `spring_ssr/src/main/java/com/ch/basic/common/config/LoginCheckInterceptor.java:23-24`
- **문제**: 클래스 Javadoc이 `excludePathPatterns(): 비로그인도 접근 가능한 URL → /login, /signup, /, /community, /community/{id}, /uploads/**, /css/**, /js/**` 라고 서술하나, 2차작업에서 WebConfig의 exclude는 **전부 제거됨**. 현재 WebConfig 주석(72-73행), 개념_07 4-1장, 개념_11 5장 모두 "exclude 없이 include만 등록"으로 올바르게 서술하고 있어 **이 Javadoc만 3곳과 정면 모순**. 강의에서 exclude 우선평가 버그 사례를 배운 직후 소스를 열면 혼란 유발. 2차작업의 WebConfig 수정 시 동기화 누락으로 판단됨.
- **수정 제안**: 23-24행을 "excludePathPatterns()는 사용하지 않음 — 로그인 필요 4개 경로만 addPathPatterns()로 명시 등록하므로 그 외 경로는 애초에 적용되지 않음 (WebConfig 참고)"로 교체.

### M4. `개념_06_Transaction.md:90` — 내부 호출 "트랜잭션 적용 안 됨" 부정확

- **위치**: `docs/spring_ssr/개념_06_Transaction.md:81-98` (4장 예제)
- **문제**: `sendNotification(); // ❌ 트랜잭션 적용 안 됨!` — 사실이 아님. `createCommunity()`가 `@Transactional`이므로 내부 호출된 `sendNotification()`의 코드는 **호출자(바깥) 트랜잭션 안에서 실행**됨. 프록시를 우회해 무시되는 것은 `REQUIRES_NEW`(새 트랜잭션 분리) 속성. 95-97행의 "@Transactional이 무시됨"도 같은 오해를 유발. 초보자가 "내부 호출이면 트랜잭션이 아예 없다"는 잘못된 멘탈 모델을 갖게 됨 — 관리자가 원문 직접 확인.
- **수정 제안**: `// ❌ REQUIRES_NEW가 무시됨! (새 트랜잭션으로 분리되지 않고, 바깥 트랜잭션에 그대로 포함되어 실행)`으로 변경하고 95-97행 주석도 "어노테이션의 전파 속성이 무시됨"으로 정밀화.

## 낮음 (선택 반영 — 다음 작업 차수 일괄 처리 가능)

### L1. `개념_06_Transaction.md:109-121` — 한 코드 펜스에 동일 시그니처 `process()` 2개

5장 예제가 하나의 ```java 블록 안에 `public void process() throws IOException`을 두 번 선언 — 그대로 한 클래스에 넣으면 중복 메서드로 컴파일 불가. 블록을 둘로 분리하거나 두 번째를 `processWithRollback()` 등으로 개명.

### L2. `개념_09_Exception.md:142` — "같은 패턴으로 4개 존재" 부정확

실제 `ApiExceptionHandler.handleBusiness()`(ApiExceptionHandler.java:46-51)는 예시의 404 핸들러처럼 고정 상태코드가 아니라 `e.getStatus()`를 동적으로 사용. "같은 패턴"대로 독자가 400 고정 핸들러를 재현하면 같은 문서 126행 각주("API는 409 정상 반환")가 성립하지 않아 자기모순. → "(일부 발췌 — BusinessException 핸들러는 고정 상태코드 대신 `e.getStatus()` 사용)"으로 정밀화.

### L3. `개념_07_Session_Login.md:146-148` — 댓글 API 401 과잉 일반화

"CommentApiController가 자체 세션 체크 → 비로그인 시 401"은 **작성/수정/삭제만** 해당(CommentApiController 73·105·132행). 목록 GET(46-54행)은 세션 체크 없이 비로그인도 200. → "댓글 작성/수정/삭제 시 자체 세션 체크로 401 반환 (목록 조회는 비로그인도 가능)"으로 정정.

### L4. `개념_11_Filter_Interceptor.md:141` — "Filter는 Spring Bean 사용 어렵" 표기가 같은 문서 예제와 상충

4장 비교표의 "Spring Bean 사용: 어렵(가능은 함)"은 레거시 web.xml 등록 방식에만 해당. 같은 문서 41행 예제는 `@Component` Filter라 DI가 자유로움 — 초보자가 모순을 느낌. → "서블릿 컨테이너 직접 등록 시 주입 불가, Spring Boot에서 @Component/FilterRegistrationBean 등록 시 가능"으로 조건 명시.

### L5. 고아 파일 24시간 유예가 문서 의도대로 동작하지 않을 수 있음

`FileRepository.java:36-47`의 고아 처리(`updateRefIdForIds`, `detachFiles*`)는 JPQL 벌크 `@Modifying` UPDATE라 `FileEntity.@PreUpdate`가 호출되지 않아 `updatedAt`이 갱신되지 않음. 스케줄러(`FileCleanupScheduler` → `FileService.deleteOrphanFiles`)는 `updatedAt < now-24h` 기준이므로, 실제 유예 기준은 "고아가 된 시점"이 아니라 "마지막 엔티티 갱신(사실상 업로드) 시점". 업로드 후 24시간이 지난 파일이 재-고아 처리되면 다음 새벽 4시에 즉시 삭제됨. → 벌크 쿼리에 `f.updatedAt = CURRENT_TIMESTAMP`를 함께 set하거나, 문서(프로젝트_구조_정리.md:252 등)에서 기준을 정확히 기술.

### L6. 댓글 수정/삭제 시 `{communityId}` 경로 변수 미검증

`CommentApiController.java:98-139` — `commentId`만으로 처리하고 URL의 `communityId`가 해당 댓글의 실제 소속 게시글인지 확인하지 않음. 소유자 검증(`isWrittenBy`)이 있어 보안 문제는 아니나, `DELETE /api/communities/999/comments/5`처럼 잘못된 상위 리소스로도 동작해 REST 계층 정합성이 깨짐. → 서비스에서 소속 일치 검증 후 불일치 시 404, 또는 문서에 의도적 단순화임을 명시.
