## ch9_웹브라우저동작원리

총평: 렌더링 파이프라인(파싱→DOM/CSSOM→렌더트리→레이아웃→페인트→합성), 리플로우/리페인트 구분표, transform vs left, 강제 동기 레이아웃, 캐시/ETag/DevTools 설명은 입문 수준에서 대체로 정확하고 문서↔소스 일관성도 좋음. 다만 "성능 측정" 실습 일부가 실제로는 리플로우를 측정하지 못하고, "appendChild 할 때마다 리플로우"라는 서술이 브라우저의 레이아웃 배치(지연) 처리와 어긋남.

### 높음
- 해당 없음 (명백한 치명적 사실 오류 없음)

### 중간
- `javascript_basic/ch9_웹브라우저동작원리/part01_성능최적화실습.html:235-245, 248-261, 264-276` — 스타일 변경 최적화 실습(`testSlowStyle`/`testFastStyle`/`testCssText`)의 `performance.now()` 측정 구간이 인라인 스타일 대입 코드만 감쌈. 리플로우는 대입 시점이 아니라 이후 레이아웃이 필요할 때 계산되므로 측정값은 사실상 JS 대입 시간(≈0ms)일 뿐 리플로우 비용이 아님 → "개별 style vs classList vs cssText" 비교가 의도대로 유의미하게 안 나올 수 있음. `offsetWidth` 강제 읽기를 넣어야 실제 대비됨. (참고: `testForcedReflow`는 `offsetWidth`를 읽어 정상 대비됨)
- `javascript_basic/ch9_웹브라우저동작원리/part01_성능최적화실습.html:172, 182` — 결과 문구 "매번 appendChild할 때마다 리플로우가 발생합니다"는 부정확. 현대 브라우저는 레이아웃을 즉시 계산하지 않고 배치(지연)하므로, 루프 중 레이아웃을 강제로 읽지 않는 한 1000번의 동기 리플로우는 발생하지 않음. DocumentFragment가 빠른 주된 이유는 리플로우 횟수보다 live-DOM 조작 비용 차이.
- `docs/javascript_basic/ch9_웹브라우저동작원리/강의노트_9장_웹브라우저동작원리.md:561, 569, 695, 712` — 같은 취지("100번 리플로우!", "매번 리플로우!", "총 2번의 리플로우만"). append 횟수만큼 동기 리플로우가 난다는 뉘앙스는 브라우저 레이아웃 배치 처리와 어긋남. "DOM 변경이 레이아웃을 무효화(invalidate)하고, 강제로 읽거나 렌더 시점에 리플로우가 일어난다"로 다듬기 권장.
