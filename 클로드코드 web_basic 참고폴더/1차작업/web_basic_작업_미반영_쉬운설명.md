## ① ch01 — "서블릿은 싱글톤 인스턴스로 관리된다"

**1. 검수자가 뭐라고 했나?**
"서블릿이 싱글톤이다"라는 말은 엄밀히 따지면 정확한 표현이 아니다. 그대로 둬도 되지만 확인해 봐라. (검수자도 "오류로 단정하지 않음"이라고 적음)

**2. 이게 무슨 얘기인가?**
- **싱글톤(Singleton)** = "이 클래스의 객체(인스턴스)는 프로그램 전체에서 딱 1개만 존재한다"는 규칙.
- 서블릿은 톰캣이 보통 **1개만 만들어서** 여러 요청이 그 하나를 나눠 쓴다. 그래서 흔히 "서블릿은 싱글톤"이라고 가르친다.
- 검수자의 지적: 엄밀히는 "프로그램에 무조건 1개"라는 진짜 싱글톤(GoF 디자인 패턴)이 아니라, **"web.xml에 서블릿을 선언한 개수만큼"** 만들어진다. 즉 같은 서블릿 클래스를 다른 URL 두 개에 각각 등록하면 인스턴스가 2개가 될 수도 있다. 그래서 "정확히는 싱글톤은 아니다"라는 것.

**3. 왜 안 고쳤나?**
- 실무·강의에서 **거의 모두 "서블릿은 싱글톤"이라고 단순화해서** 가르친다. 초보자가 처음 이해할 땐 "요청마다 새로 만들어지지 않고, 하나를 공유한다"는 감을 잡는 게 훨씬 중요하다.
- 지금 프로젝트는 서블릿을 URL 하나에만 등록하므로 실제로도 1개다. 소스 주석과도 말이 맞는다.
- 검수자 본인도 "오류로 단정하지 않음, 그대로 둬도 무방"이라고 했다.

**4. 그래도 알아둘 점**
- 나중에 깊이 들어가면 "정확히는 *선언당 인스턴스 1개*"라고 알아두면 된다. 지금 단계에선 "서블릿은 공유되는 하나의 객체" 정도로 이해하면 충분하다.

**▶ 최종 처리: 반영(문서)** — ch01 문서에 괄호로 한 줄 언급 추가.
> "(엄밀히는 '선언(등록)당 인스턴스 1개'라 순수 싱글톤과는 다르지만, 처음에는 '요청마다 새로 만들지 않고 하나를 공유한다' 정도로 이해하면 충분하다.)"

## ② ch10 — InMemoryBoardDao 페이징 경계 잠재 버그 (subList)

**1. 검수자가 뭐라고 했나?**
`InMemoryBoardDao`의 페이징 코드가, 특정 상황에서 에러(`IllegalArgumentException`)를 낼 수 있는 잠재 버그가 있다. 지금은 안 터지지만 결함이다.

**2. 이게 무슨 얘기인가?**
- 페이징 = 게시글이 많을 때 "1페이지는 1~10번, 2페이지는 11~20번" 이렇게 잘라서 보여주는 것.
- 코드가 리스트에서 `subList(from, to)`로 "from번째부터 to번째까지 잘라내"를 한다.
- 문제 상황: 데이터가 1개뿐인데 "11번째부터 보여줘(offset=10)"라고 요청하면, `from(10)`이 `to(1)`보다 커진다 → `subList(10, 1)`은 말이 안 되는 요청이라 **에러가 난다.**
- 비유: 사과가 1개 있는데 "11번째 사과부터 집어줘"라고 하면 프로그램이 "그런 건 없는데?" 하고 뻗는 것.

**3. 왜 안 고쳤나?**
- **지금은 절대 안 터진다.** 현재 컨트롤러는 항상 `selectList(null)`(전체 목록)로만 호출해서, offset 같은 값을 넘기지 않기 때문이다.
- 이 In-memory DAO는 "MyBatis 배우기 전 임시 연습용"이고, 원래 계획은 나중에 **MyBatis(진짜 DB)로 교체**하는 것이다. 그 교체 자체가 수강생 실습 과제라, 지금 임시 코드를 굳이 손대면 오히려 실습 흐름이 지저분해진다.
- 그래서 소스는 그대로 두고, **문서(ch10)에 "이런 경계 주의가 있다"고 적어**뒀다.

**4. 그래도 알아둘 점**
- 정 고치고 싶으면 딱 한 줄이면 된다:
  ```java
  // from 값이 리스트 크기를 넘지 않도록 상한을 씌운다
  int from = Math.min(list.size(), Math.max(0, offset));
  ```
- "잘라내기 범위가 데이터 개수를 넘지 않는지 확인"하는 건 페이징에서 늘 나오는 단골 주의점이다.

**▶ 최종 처리: 반영(소스 수정)** — `Math.max/Math.min`으로 고쳤다. 이 함수 자체가 "from/to 경계를 신경 써야 한다"는 걸 실습생이 인식하게 하는 효과가 있어 수정하는 쪽을 택함.
> ```java
> // from에도 상한(list.size())을 씌워 from > to 를 방지
> int from = Math.min(list.size(), Math.max(0, offset));
> int to   = Math.min(list.size(), from + limit);
> ```

## ③ 실습용 JSP의 보안 약점 (XSS / 숫자 파싱) — 소스는 안 고치고 문서에만 주의 표기

**1. 검수자가 뭐라고 했나?**
데모 JSP 몇 개가
- 사용자가 입력한 값을 그대로 화면에 출력한다 → **XSS**(악성 스크립트 삽입) 위험.
- `Integer.parseInt(...)`로 숫자를 변환하는데, 숫자가 아닌 값이 들어오면 **500 에러**.

**2. 이게 무슨 얘기인가?**
- **XSS(반사형)**: 사용자가 입력창에 `<script>나쁜코드</script>` 같은 걸 넣었을 때, 서버가 그걸 **그대로 화면에 다시 뿌리면** 브라우저가 그 스크립트를 실행해 버린다. 값을 출력하기 전에 `<`, `>` 같은 특수문자를 안전한 글자로 바꿔주면(이스케이프) 막힌다. JSTL의 `<c:out>`이나 EL이 이걸 해준다.
- **parseInt 에러**: `?page=3`처럼 숫자가 오면 정상인데, `?page=abc`처럼 글자가 오면 "이건 숫자로 못 바꿔!" 하고 프로그램이 뻗어서(예외) 500 에러 페이지가 뜬다.

**3. 왜 (소스는) 안 고쳤나?**
- 이 파일들은 **"개념을 보여주는 데모"**라서 일부러 짧고 단순하게 만든 것이다. 방어 코드(try/catch, 이스케이프)를 넣으면 코드가 길어져서, 정작 가르치려는 핵심(쿠키·세션·페이징 원리)이 가려진다.
- 그래서 **소스는 단순하게 두고**, 대신 **문서(ch05, ch11)에 "이건 데모라서 이렇지, 실무에선 이렇게 막아야 한다"**고 주의 문구를 넣었다.

**4. 그래도 알아둘 점**
- 실무 규칙 2개만 기억하면 된다:
  1. 화면에 사용자 입력을 출력할 땐 **`<c:out>`/EL로 이스케이프** (그냥 `<%= %>`로 날것 출력 금지).
  2. 문자열을 숫자로 바꿀 땐 **try/catch로 감싸거나 기본값**을 준다.
     ```java
     int page = 1;
     try { page = Integer.parseInt(pageStr); } catch (Exception e) { page = 1; }
     ```

**▶ 최종 처리: 미반영(그대로 둠)** — 처음 배우는 단계라 "파라미터를 이렇게 받아 처리한다"는 흐름을 보여주는 게 목적. 모든 예외 상황을 하나하나 막는 코드는 지금 단계엔 너무 어렵고 핵심을 흐린다. 소스는 단순하게 두고, 실무 주의만 문서(ch05·ch11)에 남겨둠. (XSS 주의 문구도 문서에 유지)

## ④ ch12 — 문서의 `INSERT INTO code VALUES(...)` 예시가 실제 SQL 파일과 형태가 다름

**1. 검수자가 뭐라고 했나?**
문서의 예시는 `INSERT INTO code VALUES('board_status','A','활성')`처럼 값 3개만 넣는데, 실제 `code_table.sql` 파일은 컬럼이 4개(`id` 포함)라서, 문서 예시 그대로 실행하면 실패한다.

**2. 이게 무슨 얘기인가?**
- DB 테이블에 값 넣기: `INSERT INTO 테이블 VALUES(...)`.
- 컬럼 이름을 안 적고 `VALUES(...)`만 쓰면, **테이블의 모든 컬럼에 순서대로** 값을 채워야 한다.
- 실제 테이블엔 `id`(자동 증가), `category`, `code`, `label` 이렇게 4칸이 있다. 그런데 문서 예시는 값을 3개만 줬으니 "칸 개수가 안 맞아!" 하고 거절당한다.
- 반대로 실제 sql 파일은 `INSERT INTO code(category, code, label) VALUES(...)`처럼 **넣을 컬럼을 콕 집어서** 3개만 넣기 때문에 정상 동작한다.

**3. 왜 안 고쳤나?**
- 문서의 예시는 "코드 테이블이라는 게 대충 이렇게 생겼다"를 보여주는 **개념 설명용 단순 예시**다. 실제 실행하라고 준 파일이 아니다.
- 검수자도 "문서 예시는 그 자체로 틀린 건 아니다"라고 했다. 실제 파일(`code_table.sql`)은 이미 올바르게 되어 있다.
- 그래서 개념 예시는 단순함을 유지하려고 그대로 뒀다. (문서를 실행 파일처럼 오해하지만 않으면 문제없음)

**4. 그래도 알아둘 점**
- 실무 팁: `INSERT`할 땐 **항상 컬럼명을 적어라.**
  ```sql
  INSERT INTO code (category, code, label) VALUES ('board_status', 'A', '활성');
  ```
  이렇게 하면 테이블 컬럼이 나중에 바뀌어도 덜 깨지고, 어떤 값이 어디 들어가는지 명확하다.

**▶ 최종 처리: 반영(문서 수정)** — "설명과 실제 코드가 맞아야 한다"는 원칙에 따라, ch12 문서 예시를 실제 `code_table.sql`과 동일하게 맞췄다. `CREATE TABLE`에 `id INT AUTO_INCREMENT PRIMARY KEY` 포함, `INSERT INTO code(category, code, label) VALUES(...)`로 **컬럼 명시**(모든 컬럼 적기가 기본).
