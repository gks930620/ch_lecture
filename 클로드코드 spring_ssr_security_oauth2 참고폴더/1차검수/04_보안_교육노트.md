> **오류가 아닙니다.** 현재 코드는 학습용으로 정상 동작합니다.
> 다만 "실무에서는 이렇게 한다"를 짚어주면 초심자에게 좋은 지점들입니다.

## ⚪ [8] `anyRequest().permitAll()` — 기본 허용 정책

**파일**: `SecurityConfig.java` 43행

```java
.requestMatchers("/", "/login", "/signup").permitAll()
.requestMatchers("/admin").hasAuthority("ADMIN")
.requestMatchers("/mypage").hasAnyAuthority("ADMIN", "USER")
.anyRequest().permitAll()      // ← 명시하지 않은 모든 URL을 허용
```

- 지금은 `/admin`, `/mypage`만 보호하고 **나머지 모든 URL을 열어둡니다.**
- 실무 관례는 마지막을 `anyRequest().authenticated()`(기본 차단)로 두고, 열어줄 것만 `permitAll()` 하는 **화이트리스트 방식**입니다.
- **교육 노트 제안**: *"학습 편의로 나머지를 permitAll 했지만, 실무에서는 `anyRequest().authenticated()`로 기본 차단 후 필요한 경로만 열어주는 것이 안전하다."*

## ⚪ [9] `hasAuthority("ADMIN")` vs `hasRole("ADMIN")` (ROLE_ 접두어)

**파일**: `SecurityConfig.java`, `CustomUserAccount.getAuthorities()`

이 프로젝트는 권한을 `"ADMIN"`, `"USER"` 문자열 **그대로** 부여하고(`() -> role`), `hasAuthority("ADMIN")`으로 검사합니다. **내부적으로 일관되어 정상 동작**합니다.

- 다만 초심자가 흔히 만나는 함정: **`hasRole("ADMIN")`은 이 구조에서 동작하지 않습니다.**
  - `hasRole("ADMIN")`은 내부적으로 `ROLE_ADMIN` 권한을 찾기 때문입니다.
  - 이 프로젝트 권한에는 `ROLE_` 접두어가 없으므로 `hasRole`을 쓰면 항상 403이 됩니다.
- **교육 노트 제안**: *"`hasAuthority`는 문자열 그대로 비교, `hasRole`은 `ROLE_` 접두어를 자동으로 붙여 비교한다. 이 프로젝트는 접두어 없이 `hasAuthority`로 통일했다."* 한 줄이면 혼란을 크게 줄입니다.

## ⚪ [10] KAKAO `id` 캐스팅 견고성

**파일**: `OAuthProvider.java` 57행

```java
Long id = (Long) attributes.get("id");  // 카카오는 id가 Long
```

- 카카오 사용자 id는 크므로 대부분 `Long`으로 역직렬화되어 **정상 동작**합니다.
- 다만 JSON 숫자는 값 크기에 따라 `Integer`로 올 여지가 이론상 있어, 그 경우 `ClassCastException`이 납니다.
- **개선(선택)**: `Number`로 받아 견고하게 처리.
  ```java
  Object idObj = attributes.get("id");
  String id = String.valueOf(idObj);   // username은 어차피 문자열로 이어붙임
  ```
  현재도 `provider + id` 로 문자열을 만들 뿐이라 굳이 `Long`으로 캐스팅할 필요는 없습니다.
