# 03. 구조 · 강의 범위 정리 제안

> 오류는 아니지만, "처음 개발을 시작하는 사람" 기준에서 **혼란을 줄이기 위한** 제안입니다.
> 이 프로젝트의 실제 기능은 **로그인(폼 + OAuth2) / 회원가입 / 마이페이지 / 관리자 페이지**가 전부입니다.
> 그런데 그와 무관한 보일러플레이트 잔재가 코드·설정·문서에 남아 있습니다.

---

## 🟡 [3] 프로젝트 기능과 무관한 잔재 코드/설정

이 로그인 프로젝트에는 아래 요소들이 **선언만 되어 있고 실제로 쓰이는 곳이 없습니다.**

| 잔재 | 위치 | 실제 사용처 |
|------|------|-------------|
| QueryDSL | `build.gradle`(의존성), `QuerydslConfig.java`, `querydslDir` sourceSet | **없음** — QClass·JPAQueryFactory를 쓰는 Repository 0개 |
| 파일 업로드 | `application.yml`의 `servlet.multipart`, 커스텀 `file.upload-dir`, `uploads/` 폴더 | **없음** — MultipartFile을 받는 Controller 0개 |
| 소프트 삭제 | `UserEntity`의 `@SQLRestriction`, `isDeleted`, `softDelete()` | **없음** — 사용자 삭제 기능 자체가 없음 |
| N+1 완화 | `application.yml`의 `default_batch_fetch_size: 100` | **없음** — 연관관계 엔티티 0개 |

### 왜 문제인가
초심자는 "이 설정/클래스가 왜 있지? 로그인이랑 무슨 관계지?"에서 막힙니다. 특히 QueryDSL은 빌드 설정(annotationProcessor, sourceSets)까지 얽혀 있어 "로그인 배우러 왔는데 QueryDSL을 왜 세팅하지?"가 됩니다.

### 조치 제안 (택1)
1. **(강의 목적이 '순수 Security/OAuth2'라면)** 위 잔재를 **제거**하여 프로젝트를 로그인에 집중시킵니다. → 가장 깔끔.
2. **(공통 보일러플레이트를 의도적으로 유지한다면)** 문서 어딘가에 *"이 요소들은 다른 프로젝트와 공유하는 보일러플레이트이며 본 로그인 예제에서는 사용하지 않는다"* 를 한 줄 명시.

> 판단은 강의 설계 의도에 달렸습니다. 다만 **아무 설명 없이 방치**된 지금 상태는 초심자에게 노이즈입니다.

## 🟡 [4] `프로젝트_구조_정리.md`의 상당 부분이 이 프로젝트와 무관

**파일**: `docs/spring_ssr_security_oauth2/프로젝트_구조_정리.md`

이 문서의 앞부분(1~35행, 130~148행)은 **댓글/게시글/파일 업로드가 있는 CRUD 프로젝트**를 전제로 합니다.

- "글1 - 댓글N", "글 상세보기 화면", "댓글 목록 IN 쿼리" (133~143행)
- "CSR은 1 API = 1 Controller = 1 Service", "Facade 패턴" (10~16행)
- "html CSS 는 현재 피그마에맞게" (1~2행)

그러나 이 프로젝트에는 **게시글·댓글·파일 도메인이 전혀 없습니다.** 로그인 전용입니다.

### 조치 제안
- 이 문서는 여러 프로젝트가 공유하는 **범용 아키텍처 원칙 문서**로 보입니다.
- 로그인 프로젝트의 docs에 그대로 두면, 초심자는 "댓글? 글? 이 프로젝트 어디에 있지?" 하고 코드에서 찾다 헤맵니다.
- **로그인/User/DTO 분리/Security 관련 절(37~128행)만 남기고**, 게시글·댓글·Facade·연관관계 부분은 분리하거나 "범용 원칙(이 프로젝트에는 미적용)" 임을 명시하는 것을 권장합니다.

> 반대로, 이 문서를 "전 강의 공통 원칙 모음"으로 의도한 것이라면 index.md나 문서 상단에 *"이 문서는 전체 강의 공통 아키텍처 원칙이며, 로그인 프로젝트에는 일부만 해당한다"* 를 명시하면 혼란이 줄어듭니다.
