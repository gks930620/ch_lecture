# ch12 문제답안

[← ch12 문서로](../ch12_트랜잭션.md)

## 1. 계좌이체와 트랜잭션

트랜잭션 없이 실행하면: 출금 UPDATE 만 성공하고 입금 UPDATE 전에 장애(정전, 프로그램 다운)가 나면 **A 의 돈만 사라진 상태로 남는다.**

트랜잭션으로 묶으면: 두 UPDATE 는 COMMIT 되기 전까지 확정되지 않는다.

- 둘 다 성공했을 때만 COMMIT → 두 변경이 동시에 확정
- 중간에 실패하면 ROLLBACK(비정상 종료 시 자동 ROLLBACK) → 출금까지 전부 취소

즉 "둘 다 반영" 아니면 "둘 다 없던 일" 두 가지 상태만 가능하고, 돈만 사라지는 중간 상태는 존재할 수 없다(원자성).

## 2. SAVEPOINT 추적

```sql
INSERT INTO DEPT VALUES (60, '법무팀', '서울');   -- ①
SAVEPOINT A;
UPDATE EMP SET BONUS = 999 WHERE EMP_ID = 1001;   -- ②
SAVEPOINT B;
DELETE FROM ORDERS WHERE ORDER_ID = 5001;         -- ③
ROLLBACK TO A;    -- ②, ③ 취소 (A 이후 전부)
COMMIT;           -- 남아 있는 ① 확정
```

**최종적으로 남는 것: ① 법무팀 INSERT 뿐이다.**  
`ROLLBACK TO A` 가 A 지점 이후의 UPDATE 와 DELETE 를 모두 취소하고, COMMIT 이 그 앞의 INSERT 를 확정한다.

## 3. DDL 자동 COMMIT 함정

**5002번 주문은 살아나지 않는다. 이미 삭제 확정이다.**

`CREATE TABLE TEMP1` (DDL) 이 실행되는 순간 **자동 COMMIT** 이 일어나서, 그 직전의 DELETE 까지 확정되어 버렸다.  
마지막 `ROLLBACK` 은 되돌릴 것이 없는 상태에서 실행된 것이므로 아무 효과가 없다.

## 4. 잠금과 읽기 일관성

- (a) 세션 B 의 UPDATE 는 **실행되지 않고 대기(블로킹)한다.** 세션 A 가 1005번 행에 잠금을 쥐고 있기 때문이다. A 가 COMMIT 또는 ROLLBACK 하는 순간 B 의 UPDATE 가 이어서 실행된다.
- (b) SELECT 는 기다리지 않고 즉시 결과가 나오며, **변경 전 값인 3200** 으로 보인다. 오라클은 커밋되지 않은 남의 변경을 절대 보여주지 않는다(읽기 일관성).

## 5. 실습 재현 순서

1. SQL Developer 에서 같은 계정으로 접속을 2개 연다. (새 워크시트가 아니라 **새 접속**이어야 세션이 나뉜다. 접속 노드에서 마우스 오른쪽 → 접속 열기, 또는 워크시트의 "전용 접속" 사용)
2. 세션 A: `UPDATE EMP SET SALARY = 9999 WHERE EMP_ID = 1005;` 실행. COMMIT 하지 않는다.
3. 세션 B: `SELECT SALARY FROM EMP WHERE EMP_ID = 1005;` → 3200 (변경 전 값).
4. 세션 B: `UPDATE EMP SET SALARY = 7777 WHERE EMP_ID = 1005;` → 실행이 끝나지 않고 멈춰 있다.
5. 세션 A: `COMMIT;` → 그 순간 세션 B 의 UPDATE 가 완료된다.
6. 세션 B: `COMMIT;` 후 조회하면 최종 월급은 7777. (나중에 커밋한 변경이 남는다)
7. 실습이 끝나면 실습테이블.sql 을 다시 실행해 초기화한다.
