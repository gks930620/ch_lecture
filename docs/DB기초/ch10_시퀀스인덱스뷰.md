# ch10_시퀀스인덱스뷰

---

## 학습 목표
- 시퀀스로 기본키 번호를 자동 생성할 수 있다.
- 인덱스가 왜 조회를 빠르게 하는지, 왜 아무 데나 만들면 안 되는지 안다.
- 뷰를 만들어 복잡한 쿼리를 재사용할 수 있다.

테이블 말고도 DB 에는 여러 **객체(object)** 가 있다. 실무 빈도가 높은 세 가지를 다룬다.

---

## 1. 시퀀스 (SEQUENCE) — 번호 자동 생성기

게시글 번호, 주문 번호 같은 기본키는 "겹치지 않는 새 번호"가 계속 필요하다.  
`MAX(ID) + 1` 로 하면 될 것 같지만, **두 사용자가 동시에 INSERT 하면 같은 번호를 받아** 충돌한다.  
시퀀스는 동시에 요청해도 절대 겹치지 않는 번호를 나눠 주는 객체다.

```sql
CREATE SEQUENCE SEQ_BOARD
    START WITH 1        -- 1부터
    INCREMENT BY 1;     -- 1씩 증가
```

사용:

```sql
-- 다음 번호 꺼내기 (꺼낼 때마다 증가)
SELECT SEQ_BOARD.NEXTVAL FROM DUAL;   -- 1, 실행할 때마다 2, 3, ...

-- 현재 번호 확인 (이 세션에서 NEXTVAL 을 한 번은 쓴 후에만 가능)
SELECT SEQ_BOARD.CURRVAL FROM DUAL;

-- 실전: INSERT 에서 바로 사용 (BOARD 는 아래 참고 주석 확인)
INSERT INTO BOARD (BOARD_ID, WRITER_ID, TITLE, CATEGORY)
VALUES (SEQ_BOARD.NEXTVAL, 1002, '첫 글입니다', '자유');
```

> 위 `BOARD` 테이블은 실습테이블.sql 에 없다. ch9 문제 1에서 만든 게시판 테이블을 재사용한 예시다.  
> 만들지 않은 상태에서 그대로 실행하면 `ORA-00942: table or view does not exist` 가 난다. 시퀀스 자체 실습(NEXTVAL/CURRVAL)은 BOARD 없이도 된다.

특징과 주의점:

- 시퀀스는 **테이블과 독립**이다. 어느 테이블에도 쓸 수 있지만, 관례상 테이블당 하나씩 만들어 이름으로 구분한다(`SEQ_BOARD`).
- ROLLBACK 해도 **꺼낸 번호는 되돌아가지 않는다.** 그래서 중간에 빈 번호가 생길 수 있고, **그게 정상이다.** (번호는 유일하면 되는 것이지 연속일 필요가 없다)
- 또 하나: 시퀀스는 성능을 위해 번호를 미리 메모리에 담아 둔다(기본 `CACHE 20`, 20개씩). DB 가 재시작되면 캐시에 남아 있던 번호가 날아가서 역시 구멍이 생기는데, 이것도 정상이다.
- 삭제: `DROP SEQUENCE SEQ_BOARD;`

> 참고: 오라클 12c부터는 컬럼에 `GENERATED AS IDENTITY` 를 붙여 시퀀스 없이 자동 증가를 만들 수도 있다.  
> 하지만 기존 실무 코드는 대부분 시퀀스 방식이므로 시퀀스를 확실히 알아두자.

## 2. 인덱스 (INDEX) — 조회 가속 장치

### 2.1 원리

책 뒤의 "찾아보기"를 생각하면 된다.  
인덱스가 없으면 오라클은 조건에 맞는 행을 찾기 위해 **테이블 전체를 처음부터 끝까지 읽는다**(Full Table Scan).  
100만 건 중 1건을 찾아도 100만 건을 다 읽는다.

인덱스는 특정 컬럼 값을 **정렬된 상태로 따로 저장**해 두고, 각 값이 테이블 어디에 있는지(주소)를 기억한다.  
정렬되어 있으니 이진 탐색처럼 빠르게 찾는다. (오라클은 B-tree 구조 사용)

```sql
-- EMP_NAME 으로 자주 검색한다면
CREATE INDEX IDX_EMP_NAME ON EMP (EMP_NAME);

-- 두 컬럼 조합 인덱스 (DEPT_ID 로 찾고 그 안에서 JOB 으로 찾는 검색에 유리)
CREATE INDEX IDX_EMP_DEPT_JOB ON EMP (DEPT_ID, JOB);

-- 삭제
DROP INDEX IDX_EMP_NAME;

-- 내 인덱스 확인
SELECT INDEX_NAME, TABLE_NAME FROM USER_INDEXES;
```

만들고 나면 따로 **'사용하는 문법'은 없다.** `SELECT ... WHERE EMP_NAME = '김철수'` 를 실행하면 오라클이 인덱스를 탈지 알아서 결정한다(옵티마이저 자동 판단).

### 2.2 자동으로 만들어지는 인덱스

**PRIMARY KEY 와 UNIQUE 제약을 걸면 인덱스가 자동 생성된다.**  
"기본키 조회는 빠르다"의 이유가 이것이다. `WHERE EMP_ID = 1001` 은 이미 인덱스를 탄다.

### 2.3 인덱스를 아무 데나 만들면 안 되는 이유

- INSERT/UPDATE/DELETE 때마다 **인덱스도 같이 갱신**해야 한다. 인덱스가 많을수록 쓰기가 느려진다.
- 저장 공간을 추가로 차지한다.
- 값 종류가 적은 컬럼(성별 M/F 등)은 인덱스를 만들어도 효과가 거의 없다.

만들 만한 곳: **WHERE / JOIN 조건에 자주 쓰이고, 값이 다양하게 분포**하는 컬럼. (예: 회원 이메일, 주문일자, FK 컬럼)

### 2.4 인덱스가 있어도 못 타는 경우 (맛보기)

```sql
WHERE SUBSTR(EMP_NAME, 1, 1) = '김'   -- 컬럼을 함수로 감싸면 인덱스 사용 불가
WHERE EMP_NAME LIKE '%수'             -- 앞에 % 가 오면 사용 불가 ('김%' 는 가능)
```

인덱스는 "정렬된 원본 값"으로 찾기 때문에, 값을 가공해 버리면 못 쓴다. 튜닝의 세계는 깊지만, 이 두 패턴은 지금 기억해 두자.

## 3. 뷰 (VIEW) — 저장해 둔 SELECT

자주 쓰는 복잡한 SELECT 에 이름을 붙여 **가상 테이블**처럼 쓰는 객체다.

```sql
-- 사원 + 부서명 + 상사명까지 붙인 쿼리를 뷰로 저장
CREATE OR REPLACE VIEW V_EMP_DETAIL AS
SELECT E.EMP_ID,
       E.EMP_NAME,
       E.JOB,
       E.SALARY,
       D.DEPT_NAME,
       M.EMP_NAME AS MGR_NAME
FROM   EMP E
LEFT JOIN DEPT D ON E.DEPT_ID = D.DEPT_ID
LEFT JOIN EMP  M ON E.MGR_ID  = M.EMP_ID;
```

사용은 테이블과 똑같이:

```sql
SELECT * FROM V_EMP_DETAIL WHERE DEPT_NAME = '개발팀';
SELECT DEPT_NAME, COUNT(*) FROM V_EMP_DETAIL GROUP BY DEPT_NAME;
```

- `CREATE OR REPLACE` — 이미 있으면 덮어쓴다. 뷰 수정 시 편리.
- 뷰는 **데이터를 저장하지 않는다.** 조회할 때마다 원본 테이블에서 읽는다(저장된 건 SELECT 문뿐).  
  그래서 원본이 바뀌면 뷰 결과도 즉시 바뀐다.
- 삭제: `DROP VIEW V_EMP_DETAIL;` (원본 테이블은 그대로)
- 확인: `SELECT VIEW_NAME FROM USER_VIEWS;`

뷰의 용도:

1. **복잡한 쿼리 재사용** — 조인 5개짜리 쿼리를 매번 다시 쓰지 않는다.
2. **보안** — 월급 컬럼을 뺀 뷰만 다른 부서에 공개하는 식으로, 보여줄 것만 보여준다.

> 단순 뷰는 INSERT/UPDATE 도 되지만(원본에 반영), 조인/그룹핑이 들어간 뷰는 대부분 조회 전용이다. 뷰는 조회용이라고 생각하는 게 마음 편하다.

---

## 정리

- **시퀀스**: 동시 접속에도 안 겹치는 번호 생성기. `SEQ.NEXTVAL` 를 INSERT 에 바로 쓴다. 번호 구멍은 정상.
- **인덱스**: 컬럼 값을 정렬해 두고 빨리 찾는 장치. PK/UNIQUE 는 자동 생성. 쓰기 성능/공간과 맞바꾸므로 검색 조건에 자주 쓰는 컬럼에만.
- **뷰**: 이름 붙인 SELECT. 데이터는 저장하지 않으며, 재사용과 보안(컬럼 숨기기)에 쓴다.

## 문제

> 이 문제들은 ORDERS 에 주문을 **COMMIT** 하고 시퀀스/인덱스/뷰를 새로 만든다. 실습이 끝나면 실습테이블.sql 을 다시 실행해 데이터를 초기화하자. (직접 만든 객체는 `DROP SEQUENCE SEQ_ORDERS;`, `DROP INDEX IDX_ORDERS_CUSTOMER;`, `DROP VIEW V_ORDER_DETAIL;` 로 정리한다.)

1. 1000번부터 시작해 1씩 증가하는 시퀀스 `SEQ_ORDERS` 를 만드시오.
2. `SEQ_ORDERS` 를 사용해 ORDERS 테이블에 주문 1건을 INSERT 하시오.  
   (상품 2006 마우스, 담당사원 1008, 고객 '한소희', 수량 2, 주문일 오늘)
3. ORDERS 테이블의 CUSTOMER_NAME 컬럼에 인덱스 `IDX_ORDERS_CUSTOMER` 를 만드시오. 이 인덱스는 어떤 쿼리에 도움이 되는가?
4. 다음 두 조건 중 인덱스(IDX_ORDERS_CUSTOMER)를 탈 수 있는 것은 어느 쪽인가? 이유는?
   - (a) `WHERE CUSTOMER_NAME LIKE '나%'`
   - (b) `WHERE CUSTOMER_NAME LIKE '%호'`
5. "주문번호, 상품명, 담당사원명, 고객명, 주문금액(가격×수량)" 을 보여주는 뷰 `V_ORDER_DETAIL` 을 만들고, 이 뷰에서 고객별 총 주문금액을 조회하시오.
6. (생각해보기) 시퀀스로 번호를 딴 INSERT 를 ROLLBACK 하면, 다음 INSERT 는 몇 번을 받게 되는가? 이것이 문제가 되지 않는 이유는?
