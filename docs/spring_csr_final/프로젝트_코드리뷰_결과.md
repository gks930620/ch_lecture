### 1. `AppOAuth2Controller` — Refresh 토큰 DB 미저장  ✅ 수정됨
> 현재 코드: `AppOAuth2Controller.java`에 `refreshService.saveRefresh(refreshToken);` 호출이 추가되어 해결됨.

**파일:** `jwt/controller/AppOAuth2Controller.java` (line ~98)

```java
// 현재 코드: refreshToken을 생성만 하고 DB에 저장하지 않음
String accessToken = jwtUtil.createAccessToken(username);
String refreshToken = jwtUtil.createRefreshToken(username);
// ← refreshService.saveRefresh(refreshToken) 호출이 없음!
```

**문제:** 앱에서 OAuth2 로그인 후 받은 refreshToken으로 `/api/tokens/refresh` 호출 시,  
DB에 토큰이 없으므로 "폐기된 토큰" 에러 발생 → 토큰 재발급 불가

**수정:** `refreshService.saveRefresh(refreshToken);` 추가 필요

### 2. `RefreshController` — 쿠키 secure 하드코딩  ✅ 수정됨
> 현재 코드: `@Value("${app.cookie.secure:false}") private boolean secureCookie;` 주입 후 `.secure(secureCookie)` 적용되어 해결됨.

**파일:** `jwt/controller/RefreshController.java` (line ~113)

```java
private void addCookie(HttpServletResponse response, String name, String value) {
    ResponseCookie cookie = ResponseCookie.from(name, value)
            .httpOnly(true)
            .secure(false) // ❌ 하드코딩! TODO 주석만 있고 실제 미적용
            .sameSite("Lax")
            .path("/")
            .build();
```

**문제:** `JwtLoginFilter`와 `OAuth2LoginSuccessHandler`는 `@Value("${app.cookie.secure}")` 로 환경별 분기하는데,  
`RefreshController`만 `false` 하드코딩. 운영(HTTPS) 배포 시 쿠키 보안 불일치.

**수정:** `@Value("${app.cookie.secure:false}") private boolean secureCookie;` 주입 후 사용

### 5. `UserEntity.roles` — `List<String>` JPA 매핑 문제  ⬜ 매핑 유지(3차: 설명 주석 추가)
> 3차 작업: `@ElementCollection`으로 바꾸면 스키마 + `data-users.sql` 시드까지 변경해야 해 위험 → 매핑은 그대로 두고, "왜 BLOB로 저장되는지 / 바꾸려면 어떻게 하는지"를 `UserEntity.java` 필드 주석으로 설명 추가함.

**파일:** `jwt/entity/UserEntity.java`

```java
@Builder.Default
private List<String> roles = new ArrayList<>();
```

**문제:** `@ElementCollection`이나 `@Convert` 어노테이션 없이 `List<String>`을 필드로 사용.  
JPA 기본 직렬화(Java Serialization → BLOB)에 의존하고 있으며, 실제 SQL에서도 `0xACED...` 바이너리로 저장됨.  
**동작은 하지만**, 강의에서 설명 시 "왜 이렇게 저장되는지" 혼란을 줄 수 있고, DB에서 직접 조회/수정이 불가.

**권장 개선 (선택):**
```java
@ElementCollection(fetch = FetchType.EAGER)
@CollectionTable(name = "user_roles", joinColumns = @JoinColumn(name = "user_id"))
@Column(name = "role")
@Builder.Default
private List<String> roles = new ArrayList<>();
```
> 단, 이 경우 data-users.sql도 변경 필요. 현재 방식이 의도적이라면 주석으로 설명 추가 권장.

### 9. `SecurityConfig` — `authorizeHttpRequests` 두 번 호출  ✅ 하나로 병합됨(4차)
> **정정**: "두 번 호출하면 마지막만 적용된다"는 설명은 **Spring Security 6에서는 사실이 아닙니다.**
> `http.authorizeHttpRequests(...)`는 동일 설정기를 재사용(`getOrApply`)하여 **두 블록이 누적 적용**됩니다(덮어쓰기 아님). 그래서 원래도 동작은 정상이었습니다.
> **4차 작업(정리)**: 초심자 혼란을 줄이기 위해 **중복 호출을 제거**했습니다. 첫 블록의 `/h2-console/**` permit은 이미 아래 큰 블록에 포함돼 있었고, CSRF도 바로 아래에서 전체 `disable`되므로 h2 전용 csrf 설정도 불필요 → 첫 블록에서 **`frameOptions` 비활성화만 남기고** `authorizeHttpRequests` 호출을 **하나로 통합**. 동작은 완전히 동일.

**파일:** `jwt/config/SecurityConfig.java` (단일 `authorizeHttpRequests` 블록)

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/h2-console/**").permitAll()  // 첫 번째 호출
);
// ...
http.authorizeHttpRequests(auth -> auth        // 두 번째 호출
    .requestMatchers("/css/**", ....).permitAll()
```

**원래 지적(정정됨):** "두 번 호출하면 마지막 설정만 적용되어 첫 블록이 무시될 수 있다"고 보았으나,
위 정정처럼 Spring Security 6에서는 **누적 적용**되어 무시되지 않습니다. (두 번째 블록에도 `/h2-console/**`가 있어 어차피 동작에는 영향 없음)

**권장:** 하나의 `authorizeHttpRequests()` 블록으로 통합하거나, 
H2 관련 설정을 두 번째 블록에만 남기기.

## 🟢 [잘 된 부분] — 강의용으로 훌륭한 구현

| 영역 | 평가 |
|------|------|
| **JWT 토큰 구조** | Access/Refresh 분리, token_type 클레임 활용, 만료 시 명확한 에러 코드 — 우수 |
| **필터 체인** | `JwtLoginFilter` → `JwtAccessTokenCheckAndSaveUserInfoFilter` 순서 적절, 주석 설명 상세 |
| **OAuth2 통합** | `CustomUserAccount`가 `UserDetails + OAuth2User` 동시 구현, OAuthProvider enum 패턴 — 깔끔 |
| **InMemoryAuthorizationRequestRepository** | STATELESS 환경에서 session 대신 메모리 저장, 스케줄러로 5분 후 자동 삭제 — 잘 설계됨 |
| **웹/앱 분기** | 로그인, 로그아웃, 토큰 재발급 모두 Accept 헤더 또는 토큰 위치로 분기 — 일관성 있음 |
| **게시판 CRUD** | Soft Delete, 작성자 검증, QueryDSL 동적 검색, 페이징 — 표준적 구현 |
| **댓글** | N+1 방지(fetch join), 카운트 쿼리 최적화(IN 쿼리) — 성능 고려됨 |
| **파일 시스템** | Strategy 패턴(Local/Supabase), `@ConditionalOnProperty` 활용 — 설계 패턴 학습에 좋음 |
| **STOMP 채팅** | HTTP 핸드셰이크에서 쿠키 JWT 추출 → STOMP CONNECT에서 최종 인증 — 2단계 인증 잘 구현 |
| **예외 처리** | BusinessException 계층 구조, GlobalExceptionHandler, ErrorResponse 통일 — 우수 |
| **API 응답 통일** | `ApiResponse<T>`, `PageResponse<T>`, `ErrorResponse` 구조 일관성 — 강의용으로 적합 |
