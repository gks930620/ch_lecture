# ch11 제네릭 — 문제 예시 답안

> 답은 한 가지가 아닙니다. 아래는 예시 답안이며, 스스로 푼 뒤에 비교해 보세요.

## A. 제네릭 기초

### A-1 ~ A-2. `Box<T>` 작성 + `Box<String>`, `Box<Integer>` 사용

```java
class Box<T> {
    private T value;

    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

public class BoxMain {
    public static void main(String[] args) {
        Box<String> stringBox = new Box<>();
        stringBox.set("hello");
        String s = stringBox.get();            // 캐스팅 불필요
        System.out.println(s.toUpperCase());   // HELLO

        Box<Integer> intBox = new Box<>();
        intBox.set(42);
        int n = intBox.get();                  // 오토언박싱
        System.out.println(n + 8);             // 50

        // stringBox.set(123); // 컴파일 오류: Box<String>에는 String만 넣을 수 있다
    }
}
// 출력:
// HELLO
// 50
```

**핵심 포인트**: 타입 파라미터 `T`를 쓴 이유 — "무엇을 담을지"를 사용 시점에 정하게 해서, 하나의 클래스로 모든 타입을 타입 안전하게 재사용하기 위해서다. `Object` 박스였다면 꺼낼 때마다 캐스팅이 필요하고 잘못 넣어도 컴파일러가 못 잡는다.

### A-3. raw type(`Box box`) 사용 시 경고가 발생하는 이유

```java
public class RawTypeDemo {
    public static void main(String[] args) {
        Box box = new Box();          // raw type — "unchecked" 경고 발생
        box.set("hello");             // 무엇이든 들어감 (경고)
        box.set(123);                 // Integer도 들어감 — 컴파일러가 막지 못함

        // String s = (String) box.get(); // 실행하면 ClassCastException! (마지막에 123을 넣었으므로)
        Object o = box.get();
        System.out.println(o);        // 123
    }
}
```

raw type을 쓰면 컴파일러가 타입 검사를 포기하기 때문에, 제네릭의 존재 이유(컴파일 시점 오류 차단)가 사라진다. 그 결과:

1. 어떤 타입이든 넣을 수 있어 꺼낼 때 `ClassCastException` 위험이 런타임으로 미뤄진다.
2. 컴파일러는 이 위험을 알리려고 "unchecked" 경고를 낸다.

**핵심 포인트**: raw type은 제네릭 이전(Java 5 이전) 코드와의 하위 호환을 위해서만 남아 있다. 새 코드에서는 항상 `Box<String>`처럼 타입 인자를 명시한다.

## B. 제네릭 메소드

### B-1. 두 원소를 교환하는 제네릭 swap

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class SwapDemo {
    // 배열 버전
    public static <T> void swap(T[] arr, int i, int j) {
        T tmp = arr[i];
        arr[i] = arr[j];
        arr[j] = tmp;
    }

    // 리스트 버전
    public static <T> void swap(List<T> list, int i, int j) {
        T tmp = list.get(i);
        list.set(i, list.get(j));
        list.set(j, tmp);
    }

    public static void main(String[] args) {
        String[] arr = {"a", "b", "c"};
        swap(arr, 0, 2);
        System.out.println(Arrays.toString(arr)); // [c, b, a]

        List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
        swap(list, 0, 1);
        System.out.println(list);                 // [2, 1, 3]
    }
}
```

**핵심 포인트**: 타입 파라미터 `<T>`를 메소드에 선언한 이유 — swap 로직은 원소 타입과 무관하게 동일하므로, 타입마다 메소드를 만들 필요 없이 하나로 재사용한다. 호출 시 `T`는 인자에서 자동 추론된다.

### B-2. 더 큰 값을 반환하는 제네릭 메소드

```java
public class MaxDemo {
    // T extends Comparable<T>: "자기 자신과 비교 가능한 타입"만 허용
    public static <T extends Comparable<T>> T max(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }

    public static void main(String[] args) {
        System.out.println(max(3, 7));            // 7
        System.out.println(max("apple", "kiwi")); // kiwi (사전순 비교)
        System.out.println(max(2.5, 1.9));        // 2.5

        // max(new Object(), new Object()); // 컴파일 오류: Object는 Comparable이 아님
    }
}
```

**핵심 포인트**: 경계 `T extends Comparable<T>`를 쓴 이유 — 경계가 없으면 `T`에서 `compareTo`를 호출할 수 없다(컴파일러는 T를 Object로만 취급). 경계를 선언하면 "비교 가능한 타입"이라는 계약이 API에 드러나고, 비교 불가 타입은 컴파일 단계에서 차단된다.

## C. 경계 타입

### C-1. Number 상한 제네릭으로 평균 계산

```java
import java.util.List;

public class AvgDemo {
    // T extends Number: 숫자 타입만 허용 -> doubleValue() 호출 가능
    public static <T extends Number> double avg(List<T> list) {
        if (list.isEmpty()) return 0.0;
        double sum = 0;
        for (T n : list) {
            sum += n.doubleValue();
        }
        return sum / list.size();
    }

    public static void main(String[] args) {
        System.out.println(avg(List.of(1, 2, 3, 4)));       // 2.5
        System.out.println(avg(List.of(1.5, 2.5)));         // 2.0
        System.out.println(avg(List.of(10L, 20L, 30L)));    // 20.0

        // avg(List.of("a", "b")); // 컴파일 오류: String은 Number의 하위 타입이 아님
    }
}
```

**핵심 포인트**: 상한 경계 `extends Number` 덕분에 `Integer`, `Double`, `Long` 등 어떤 숫자 리스트든 하나의 메소드로 처리하면서, 경계가 보장하는 `doubleValue()`를 안전하게 호출할 수 있다.

### C-2. Comparable 경계로 최솟값/최댓값 유틸

```java
import java.util.List;

public class MinMaxUtil {
    // Comparable<? super T>: T의 상위 타입에 정의된 compareTo도 허용 (더 유연한 표준 시그니처)
    public static <T extends Comparable<? super T>> T min(List<T> list) {
        if (list.isEmpty()) throw new IllegalArgumentException("빈 리스트");
        T result = list.get(0);
        for (T item : list) {
            if (item.compareTo(result) < 0) result = item;
        }
        return result;
    }

    public static <T extends Comparable<? super T>> T max(List<T> list) {
        if (list.isEmpty()) throw new IllegalArgumentException("빈 리스트");
        T result = list.get(0);
        for (T item : list) {
            if (item.compareTo(result) > 0) result = item;
        }
        return result;
    }

    public static void main(String[] args) {
        List<Integer> nums = List.of(5, 2, 9, 1, 7);
        System.out.println("최솟값: " + min(nums)); // 최솟값: 1
        System.out.println("최댓값: " + max(nums)); // 최댓값: 9

        List<String> words = List.of("kiwi", "apple", "mango");
        System.out.println("최솟값: " + min(words)); // 최솟값: apple
        System.out.println("최댓값: " + max(words)); // 최댓값: mango
    }
}
```

**핵심 포인트**: `Comparable<? super T>`는 부모 클래스에서 `Comparable`을 구현한 자식 타입까지 허용하기 위한 표준 관례다(`Collections.min/max`와 같은 시그니처). 입문 단계에서는 `T extends Comparable<T>`로 써도 대부분 동작한다.

## D. 와일드카드(PECS)

### D-1. `List<? extends Number>`를 읽기만 하는 메소드

```java
import java.util.List;

public class PrintAllDemo {
    // Producer(데이터를 꺼내 오기만 함) -> extends
    public static void printAll(List<? extends Number> src) {
        for (Number n : src) { // 원소가 무엇이든 최소한 Number임은 보장 -> 읽기 OK
            System.out.println(n);
        }
        // src.add(1); // 컴파일 오류: 실제 타입이 List<Double>일 수도 있어 Integer 추가 불가
    }

    public static void main(String[] args) {
        printAll(List.of(1, 2, 3));      // Integer 리스트
        printAll(List.of(1.5, 2.5));     // Double 리스트도 같은 메소드로 처리
    }
}
// 출력:
// 1
// 2
// 3
// 1.5
// 2.5
```

**핵심 포인트**: `List<Number>`로 선언하면 `List<Integer>`를 받을 수 없다(제네릭은 불공변). "Number의 하위 타입 리스트라면 뭐든 읽겠다"는 의도이므로 Producer-Extends를 선택했다.

### D-2. `List<? super Integer>`에 값을 추가하는 메소드

```java
import java.util.ArrayList;
import java.util.List;

public class AddIntsDemo {
    // Consumer(데이터를 받아 넣기만 함) -> super
    public static void addInts(List<? super Integer> dst) {
        dst.add(1); // Integer는 "Integer의 상위 타입" 어디에든 안전하게 들어간다
        dst.add(2);
        dst.add(3);
    }

    public static void main(String[] args) {
        List<Integer> ints = new ArrayList<>();
        List<Number> nums = new ArrayList<>();
        List<Object> objs = new ArrayList<>();

        addInts(ints);
        addInts(nums); // List<Number>도 받을 수 있다
        addInts(objs); // List<Object>도 받을 수 있다

        System.out.println(ints); // [1, 2, 3]
        System.out.println(nums); // [1, 2, 3]
        System.out.println(objs); // [1, 2, 3]
    }
}
```

**핵심 포인트**: `List<Integer>`로만 선언하면 `List<Number>`, `List<Object>`에는 못 넣는다. "Integer를 담을 수 있는 그릇이면 뭐든 받겠다"는 쓰기 의도이므로 Consumer-Super를 선택했다. 참고로 super 목록에서 꺼낼 때는 `Object`로만 받을 수 있다.

### D-3. extends 목록에 add가 제한되는 이유

```java
import java.util.ArrayList;
import java.util.List;

public class WhyNoAddDemo {
    public static void main(String[] args) {
        List<? extends Number> nums = new ArrayList<Double>(); // 실제로는 Double 리스트일 수 있다!

        // nums.add(1);       // 컴파일 오류: Integer를 Double 리스트에 넣으면 타입이 깨진다
        // nums.add(1.5);     // 컴파일 오류: 컴파일러는 실제 타입이 List<Integer>일 가능성도 배제 못 함
        // nums.add(null)만 유일하게 허용된다 (null은 모든 타입에 안전)

        List<? extends Number> filled = List.of(1, 2.5); // 읽기는 문제 없음
        Number first = filled.get(0);
        System.out.println(first); // 1
    }
}
```

`List<? extends Number>`의 `?`는 "Number의 하위 타입 중 **정확히 무엇인지 모르는** 어떤 하나"다. 실제 객체가 `List<Double>`일 수도 `List<Integer>`일 수도 있으므로, 컴파일러는 **어떤 값을 넣어도 안전하다고 증명할 수 없어** add를 금지한다. 반면 꺼낸 값은 무엇이든 최소한 `Number`임이 보장되므로 읽기는 허용된다.

**핵심 포인트**: "extends = 읽기(Producer), super = 쓰기(Consumer)"라는 PECS는 컴파일러가 타입 안전을 증명할 수 있는 방향만 열어 둔 결과다.

## E. 타입 소거 제약

### E-1. `new T()`가 불가능한 예제와 이유

```java
class Factory<T> {
    public T create() {
        // return new T(); // 컴파일 오류: T는 런타임에 존재하지 않는 타입이다
        return null; // 임시 처리 (E-2에서 우회)
    }
}

public class NewTDemo {
    public static void main(String[] args) {
        Factory<String> f = new Factory<>();
        System.out.println(f.create()); // null
    }
}
```

이유: Java 제네릭은 **타입 소거(Type Erasure)** 방식이라, 컴파일 후 바이트코드에서 `T`는 `Object`(또는 경계 타입)로 바뀌고 타입 인자 정보가 사라진다. 런타임에는 `T`가 `String`이었는지 알 방법이 없으므로 JVM은 어떤 생성자를 호출해야 할지 알 수 없다. 그래서 `new T()`, `T.class`, `new T[10]`이 모두 금지된다.

**핵심 포인트**: 제네릭 타입 정보는 컴파일 시점 검사용이고, 런타임에는 대부분 지워진다는 것이 자바 제네릭의 근본 제약이다.

### E-2. `Class<T>` 타입 토큰으로 우회

```java
class TokenFactory<T> {
    private final Class<T> type; // 타입 토큰: 런타임까지 살아 있는 타입 정보

    public TokenFactory(Class<T> type) { this.type = type; }

    public T create() throws ReflectiveOperationException {
        return type.getDeclaredConstructor().newInstance(); // new T() 대신 리플렉션
    }

    public boolean isInstance(Object obj) {
        return type.isInstance(obj); // instanceof T 대신 런타임 검증
    }
}

public class TypeTokenDemo {
    public static void main(String[] args) throws ReflectiveOperationException {
        TokenFactory<StringBuilder> factory = new TokenFactory<>(StringBuilder.class);

        StringBuilder sb = factory.create(); // 캐스팅 없이 T 타입으로 생성
        sb.append("token ok");
        System.out.println(sb);                          // token ok
        System.out.println(factory.isInstance(sb));      // true
        System.out.println(factory.isInstance("문자열")); // false
    }
}
```

**핵심 포인트**: `Class<T>` 객체는 소거되지 않고 런타임에 존재하므로, 생성(`newInstance`)과 타입 검증(`isInstance`)을 안전하게 대신할 수 있다. 이 패턴을 "타입 토큰"이라 하며 스프링/잭슨 등 프레임워크가 널리 사용한다.

### E-3. `instanceof List<String>`이 불가능한 이유

```java
import java.util.ArrayList;
import java.util.List;

public class InstanceofDemo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        names.add("Kim");

        // if (names instanceof List<String>) { } // 컴파일 오류: 소거로 런타임에 검사 불가
        if (names instanceof List<?> list) {       // 와일드카드 형태는 허용 (Java 16+ 패턴 매칭)
            System.out.println("List 맞음, 크기: " + list.size());
        }
    }
}
// 출력:
// List 맞음, 크기: 1
```

이유: 타입 소거 때문에 런타임의 객체에는 `List<String>`인지 `List<Integer>`인지에 대한 정보가 남아 있지 않다. 둘 다 그냥 `ArrayList` 객체일 뿐이다. 따라서 JVM은 `instanceof List<String>`이라는 질문에 답할 수 없고, 컴파일러가 이를 아예 오류로 막는다. 타입 인자를 묻지 않는 `instanceof List<?>`(또는 raw `List`)만 허용된다.

**핵심 포인트**: 런타임 타입 검사가 필요하면 원소를 꺼내 `instanceof String`으로 확인하거나, E-2처럼 `Class<T>` 토큰을 함께 들고 다니는 설계로 우회한다.

## F. 챌린지

### F-1 ~ F-2. 제네릭 캐시 `Cache<K, V>` + 만료 정책 인터페이스 분리

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

// F-2: 만료 정책을 제네릭 인터페이스로 분리 — 캐시 본체와 정책이 독립적으로 교체 가능
interface ExpirationPolicy<V> {
    boolean isExpired(V value, long storedAtMillis);
}

// 정책 구현 1: 절대 만료 없음
class NoExpiration<V> implements ExpirationPolicy<V> {
    @Override
    public boolean isExpired(V value, long storedAtMillis) {
        return false;
    }
}

// 정책 구현 2: TTL(저장 후 일정 시간) 만료
class TtlExpiration<V> implements ExpirationPolicy<V> {
    private final long ttlMillis;

    public TtlExpiration(long ttlMillis) { this.ttlMillis = ttlMillis; }

    @Override
    public boolean isExpired(V value, long storedAtMillis) {
        return System.currentTimeMillis() - storedAtMillis > ttlMillis;
    }
}

// F-1: 제네릭 캐시 — K는 키 타입, V는 값 타입 (관례적 이름 K, V 사용)
class Cache<K, V> {
    private record Entry<V>(V value, long storedAtMillis) {}

    private final Map<K, Entry<V>> store = new HashMap<>();
    private final ExpirationPolicy<V> policy;

    public Cache(ExpirationPolicy<V> policy) { this.policy = policy; }

    public void put(K key, V value) {
        store.put(key, new Entry<>(value, System.currentTimeMillis()));
    }

    public Optional<V> get(K key) {
        Entry<V> entry = store.get(key);
        if (entry == null) return Optional.empty();
        if (policy.isExpired(entry.value(), entry.storedAtMillis())) {
            store.remove(key); // 만료된 항목은 제거
            return Optional.empty();
        }
        return Optional.of(entry.value());
    }

    public int size() { return store.size(); }
}

public class CacheMain {
    public static void main(String[] args) {
        Cache<String, Integer> scoreCache = new Cache<>(new NoExpiration<>());
        scoreCache.put("kim", 95);
        scoreCache.put("lee", 88);

        System.out.println(scoreCache.get("kim").orElse(-1));  // 95
        System.out.println(scoreCache.get("none").orElse(-1)); // -1 (미존재)
        System.out.println("크기: " + scoreCache.size());       // 크기: 2

        // TTL 0ms 정책 -> 저장 직후에도 만료 처리되는지 확인
        Cache<String, String> ttlCache = new Cache<>(new TtlExpiration<>(0));
        ttlCache.put("token", "abc123");
        try { Thread.sleep(5); } catch (InterruptedException ignored) {}
        System.out.println(ttlCache.get("token").orElse("만료됨")); // 만료됨
    }
}
```

**핵심 포인트**: `K`, `V` 두 타입 파라미터로 키/값 타입을 사용 시점에 결정하고, 만료 "정책"은 `ExpirationPolicy<V>` 인터페이스로 분리해 캐시 코드를 건드리지 않고 정책만 갈아 끼울 수 있다(전략 패턴). `Optional` 반환으로 "없음"을 null 없이 표현했다.

### F-3. 잘못된 타입 사용이 컴파일 단계에서 차단되는 테스트

```java
public class TypeSafetyTest {
    public static void main(String[] args) {
        Cache<String, Integer> cache = new Cache<>(new NoExpiration<>());

        cache.put("kim", 95); // OK: 키=String, 값=Integer

        // 아래 코드는 전부 컴파일 오류 — 주석을 해제하면 빌드가 실패한다.
        // 제네릭 덕분에 잘못된 타입이 런타임까지 가지 못하고 컴파일 단계에서 차단된다.

        // cache.put(123, 95);
        //   -> 오류: 키 자리에 Integer 불가 (K=String으로 확정됨)

        // cache.put("lee", "88점");
        //   -> 오류: 값 자리에 String 불가 (V=Integer로 확정됨)

        // String score = cache.get("kim").orElse(-1);
        //   -> 오류: get의 반환은 Optional<Integer>, orElse 결과는 Integer라 String에 대입 불가

        // Cache<String, Integer> other = new Cache<String, String>(new NoExpiration<>());
        //   -> 오류: 제네릭은 불공변 — 타입 인자가 다르면 서로 대입 불가

        int score = cache.get("kim").orElse(-1); // 올바른 사용: 캐스팅 없이 Integer로 받음
        System.out.println("kim 점수: " + score); // kim 점수: 95
    }
}
```

**핵심 포인트**: "컴파일이 안 되는 것" 자체가 제네릭의 성공이다. raw type이나 `Object` 기반 설계였다면 위 네 줄이 모두 컴파일되고, 오류는 한참 뒤 런타임 `ClassCastException`으로 나타났을 것이다.
