# ch16 참고: 최신 문법과 스레드 — 문제 예시 답안

> 답은 한 가지가 아닙니다. 아래는 예시 답안이며, 스스로 푼 뒤에 비교해 보세요.
> 스레드 예제의 출력은 스케줄링에 따라 **실행마다 다를 수 있습니다**. (Java 17 기준 — switch 패턴 매칭은 preview라 사용하지 않습니다)

## A. 최신 문법

### A-1. record User(long id, String name) 정의와 사용

```java
public class RecordDemo {
    record User(long id, String name) { } // 생성자/접근자/equals/hashCode/toString 자동 생성

    public static void main(String[] args) {
        User u1 = new User(1L, "Kim");
        User u2 = new User(1L, "Kim");

        System.out.println(u1.id());        // 1        (getter 대신 컴포넌트 이름 그대로)
        System.out.println(u1.name());      // Kim
        System.out.println(u1);             // User[id=1, name=Kim]  (toString 자동)
        System.out.println(u1.equals(u2));  // true     (값 기반 equals 자동)
    }
}
```

**핵심 포인트**: record는 "불변 데이터 묶음"을 한 줄로 선언하는 문법이다. 필드가 final이라 setter가 없으며, 값이 같으면 `equals`가 true가 되어 DTO/Map 키로 쓰기 좋다.

### A-2. switch 표현식으로 주문 상태 코드 → 메시지 변환

```java
public class OrderStatusDemo {
    enum OrderStatus { ORDERED, PAID, SHIPPED, DELIVERED, CANCELED }

    static String toMessage(OrderStatus status) {
        return switch (status) { // 값을 "반환"하는 표현식, fall-through 없음
            case ORDERED -> "주문 접수됨";
            case PAID -> "결제 완료";
            case SHIPPED, DELIVERED -> "배송 단계"; // 여러 case를 콤마로 묶기
            case CANCELED -> "주문 취소됨";
        }; // enum의 모든 값을 다루면 default 생략 가능 (누락 시 컴파일 오류로 잡아줌)
    }

    public static void main(String[] args) {
        System.out.println(toMessage(OrderStatus.PAID));     // 결제 완료
        System.out.println(toMessage(OrderStatus.SHIPPED));  // 배송 단계
        System.out.println(toMessage(OrderStatus.CANCELED)); // 주문 취소됨
    }
}
```

**핵심 포인트**: 화살표(`->`) case는 break 누락으로 인한 fall-through 버그가 원천적으로 없다. enum 대상 switch 표현식은 모든 상수를 다루도록 컴파일러가 강제해 주는 것이 큰 장점이다.

### A-3. instanceof 패턴 매칭으로 타입별 분기

```java
import java.util.List;

public class InstanceofPatternDemo {
    static String describe(Object obj) {
        // instanceof 성공 시 캐스팅된 변수(s, i, list)가 바로 선언됨
        if (obj instanceof String s) {
            return "문자열(길이 " + s.length() + "): " + s;
        } else if (obj instanceof Integer i) {
            return "정수의 2배: " + (i * 2);
        } else if (obj instanceof List<?> list) {
            return "리스트(크기 " + list.size() + ")";
        }
        return "기타 타입: " + obj.getClass().getSimpleName();
    }

    public static void main(String[] args) {
        System.out.println(describe("hello"));        // 문자열(길이 5): hello
        System.out.println(describe(21));             // 정수의 2배: 42
        System.out.println(describe(List.of(1, 2)));  // 리스트(크기 2)
        System.out.println(describe(3.14));           // 기타 타입: Double
    }
}
```

**핵심 포인트**: 기존의 `instanceof 검사 → 별도 캐스팅` 2단계가 한 줄로 줄고, 잘못된 캐스팅 실수가 사라진다. switch 패턴 매칭은 Java 17에서는 preview이므로 if-else 체인의 instanceof 패턴까지만 사용한다.

### A-4. 텍스트 블록으로 멀티라인 SQL 작성

```java
public class TextBlockDemo {
    public static void main(String[] args) {
        // 기존 방식: + 연결과 \n 이스케이프로 지저분함
        String oldSql = "SELECT id, name\n"
                + "FROM users\n"
                + "WHERE status = 'ACTIVE'";

        // 텍스트 블록: 눈에 보이는 그대로가 문자열이 됨
        String sql = """
                SELECT id, name
                FROM users
                WHERE status = 'ACTIVE'
                ORDER BY id
                """; // 닫는 """의 들여쓰기 위치가 공통 들여쓰기 제거 기준

        System.out.println(sql);
        // SELECT id, name
        // FROM users
        // WHERE status = 'ACTIVE'
        // ORDER BY id
    }
}
```

**핵심 포인트**: 텍스트 블록은 줄바꿈과 따옴표를 이스케이프 없이 그대로 쓸 수 있어 SQL/JSON/HTML에 특히 유용하다. 공통 들여쓰기는 자동 제거되므로 코드 들여쓰기를 지켜도 결과물이 깨지지 않는다.

## B. var/가독성

### B-1. 명시 타입 코드를 var로 리팩터링

```java
import java.util.ArrayList;
import java.util.HashMap;

public class VarRefactorDemo {
    public static void main(String[] args) {
        // 리팩터링 전: 좌우에 타입이 중복됨
        // HashMap<String, ArrayList<Integer>> scoresByName = new HashMap<String, ArrayList<Integer>>();
        // String message = "hello";

        // 리팩터링 후: 우변만 봐도 타입이 명확하므로 var가 적합
        var scoresByName = new HashMap<String, ArrayList<Integer>>();
        var message = "hello";
        var count = 10;

        scoresByName.put("Kim", new ArrayList<>());
        scoresByName.get("Kim").add(90);

        System.out.println(message + " / " + count); // hello / 10
        System.out.println(scoresByName);            // {Kim=[90]}
    }
}
```

**핵심 포인트**: `var`는 우변(생성자, 리터럴)에 타입 정보가 이미 드러나 있을 때 중복을 없애 주는 도구다. 타입 추론은 컴파일 시점에 확정되므로 동적 타입이 되는 것이 아니다.

### B-2. var가 가독성을 해치는 예와 명시 타입 복원

```java
public class VarBadCaseDemo {
    public static void main(String[] args) {
        // 나쁜 예: 우변이 메소드 호출이라 반환 타입을 코드만 봐서는 알 수 없음
        var data = loadData();      // ??? 무슨 타입이지? List? Map? String?
        var result = process(data); // 연쇄되면 추적이 더 어려워짐

        // 수정: 메소드 반환값을 받을 때는 명시 타입으로 의도를 드러낸다
        java.util.List<String> names = loadData();
        int total = process(names);

        System.out.println(names);  // [Kim, Lee]
        System.out.println(total);  // 2
        System.out.println(data + " / " + result); // [Kim, Lee] / 2
    }

    static java.util.List<String> loadData() {
        return java.util.List.of("Kim", "Lee");
    }

    static int process(java.util.List<String> list) {
        return list.size();
    }
}
```

**핵심 포인트**: `var`의 판단 기준은 "우변만 보고 타입을 알 수 있는가"이다. 메소드 반환값처럼 타입이 코드에 드러나지 않는 곳에 쓰면 읽는 사람이 IDE 없이는 타입을 알 수 없게 된다.

### B-3. 팀 컨벤션 기준 예시

**사용해도 되는 곳**

1. 우변이 생성자 호출이라 타입이 그대로 보일 때: `var list = new ArrayList<String>();`
2. 우변이 리터럴이라 타입이 자명할 때: `var name = "Kim";`, `var count = 10;`
3. 제네릭이 길게 중첩되어 좌변 타입 선언이 오히려 소음일 때: `var entry : map.entrySet()` (for-each 루프 변수)

**금지(또는 지양)할 곳**

1. 메소드 반환값을 받을 때: `var result = service.process();` → 반환 타입을 명시
2. 숫자 리터럴의 타입이 애매할 때: `var amount = 10_000;` (long이어야 하는데 int로 추론될 수 있음)
3. 다이아몬드 연산자와 함께 써서 추론이 꼬일 때: `var list = new ArrayList<>();` → `ArrayList<Object>`로 추론됨
4. 필드/매개변수/반환 타입 — 문법상 원래 불가능하지만, 지역 변수로 우회 남용하지 않기

**핵심 포인트**: 컨벤션의 목적은 "짧은 코드"가 아니라 "리뷰어가 IDE 없이 읽어도 타입이 보이는 코드"다. 팀이 합의한 기준을 문서화하고 코드리뷰에서 일관되게 적용하는 것이 문법 자체보다 중요하다.

## C. 스레드 기초

### C-1. Runnable 기반 스레드 2개 실행 + join

```java
public class TwoThreadsDemo {
    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            String name = Thread.currentThread().getName();
            for (int i = 1; i <= 3; i++) {
                System.out.println(name + " 작업 " + i);
            }
        };

        Thread t1 = new Thread(task, "worker-1");
        Thread t2 = new Thread(task, "worker-2");

        t1.start(); // run()이 아니라 start()! (run()은 그냥 메소드 호출)
        t2.start();

        t1.join(); // t1이 끝날 때까지 main 스레드 대기
        t2.join(); // t2가 끝날 때까지 main 스레드 대기

        System.out.println("모든 작업 완료");
        // worker-1 작업 1
        // worker-2 작업 1
        // worker-1 작업 2 ... (worker-1/2의 출력 순서는 실행마다 다를 수 있음)
        // 모든 작업 완료   <- 이 줄만은 항상 마지막에 출력됨 (join 덕분)
    }
}
```

**핵심 포인트**: `start()`는 새 실행 흐름을 만들고, `join()`은 해당 스레드의 종료를 기다린다. join이 없으면 "모든 작업 완료"가 작업 도중에 먼저 찍힐 수 있다.

### C-2. ExecutorService 고정 스레드 풀로 작업 10개 실행

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class FixedPoolDemo {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3); // 스레드 3개로 고정

        for (int i = 1; i <= 10; i++) {
            final int taskNo = i; // 람다에서 쓰려면 사실상 final이어야 함
            pool.submit(() -> {
                System.out.println("작업 " + taskNo + " 처리: "
                        + Thread.currentThread().getName());
            });
        }

        pool.shutdown(); // 새 작업 접수 중단 (이미 제출된 작업은 계속 실행)
        pool.awaitTermination(10, TimeUnit.SECONDS); // 종료 대기

        System.out.println("풀 종료");
        // 작업 1 처리: pool-1-thread-1
        // 작업 2 처리: pool-1-thread-2
        // ... 작업 10개가 스레드 3개에 분배됨 (순서/담당 스레드는 실행마다 다를 수 있음)
        // 풀 종료
    }
}
```

**핵심 포인트**: 작업 10개를 위해 스레드 10개를 만들지 않고, 3개의 스레드가 큐에서 작업을 꺼내 재사용한다. `shutdown()` 없이 두면 풀 스레드가 살아 있어 JVM이 종료되지 않는다.

### C-3. Callable/Future로 비동기 계산 결과 수집

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class CallableFutureDemo {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);

        // Callable: Runnable과 달리 "값을 반환"하고 예외를 던질 수 있음
        List<Future<Integer>> futures = new ArrayList<>();
        for (int i = 1; i <= 4; i++) {
            final int n = i;
            Callable<Integer> task = () -> {
                Thread.sleep(100); // 시간이 걸리는 계산이라고 가정
                return n * n;
            };
            futures.add(pool.submit(task)); // 제출 즉시 Future를 돌려받음 (아직 결과 없음)
        }

        int sum = 0;
        for (Future<Integer> f : futures) {
            sum += f.get(); // 결과가 준비될 때까지 블로킹 후 값 수신
        }
        pool.shutdown();

        System.out.println("제곱의 합: " + sum); // 제곱의 합: 30 (1+4+9+16)
    }
}
```

**핵심 포인트**: `submit`은 기다리지 않고 즉시 `Future`(결과 예약표)를 반환하고, `get()`을 호출하는 순간에만 결과를 기다린다. 4개의 계산이 병렬로 진행되므로 총 소요 시간은 4배가 아니라 약 1회분이다.

## D. 동시성 제어

### D-1. 공유 카운터를 synchronized로 안전하게 증가

```java
public class SynchronizedCounterDemo {
    static int count = 0;
    static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 10_000; i++) {
                synchronized (lock) { // 한 번에 한 스레드만 이 블록에 진입
                    count++;
                }
            }
        };

        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();

        System.out.println(count); // 20000 (항상 정확)
    }
}
```

**핵심 포인트**: `count++`는 읽기→+1→쓰기 3단계라 중간에 끼어들면 증가분이 사라진다. `synchronized` 블록은 상호 배제(한 번에 한 스레드)를 보장해 3단계가 통째로 실행되게 만든다.

### D-2. 동일 기능을 AtomicInteger로 구현

```java
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounterDemo {
    static final AtomicInteger count = new AtomicInteger();

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 10_000; i++) {
                count.incrementAndGet(); // 하드웨어 수준의 원자 연산 (락 없음)
            }
        };

        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();

        System.out.println(count.get()); // 20000 (항상 정확)
    }
}
```

**핵심 포인트**: `incrementAndGet()`은 CPU의 CAS(compare-and-swap) 명령으로 증가 전체를 원자적으로 수행한다. 단순 카운터/플래그라면 락 기반 `synchronized`보다 가볍고 빠른 선택이다.

### D-3. volatile 플래그로 스레드 종료 제어

```java
public class VolatileFlagDemo {
    // volatile: 한 스레드의 쓰기가 다른 스레드에 "즉시 보이도록" 가시성 보장
    static volatile boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long loops = 0;
            while (running) { // volatile이 없으면 변경을 영영 못 볼 수도 있다
                loops++;
            }
            System.out.println("작업 스레드 종료 (반복 " + loops + "회)");
            // 반복 횟수는 실행마다 다를 수 있음
        });
        worker.start();

        Thread.sleep(100);   // 잠시 실행하게 둔 뒤
        running = false;     // main 스레드가 종료 신호를 보냄
        worker.join();

        System.out.println("main 종료");
        // 작업 스레드 종료 (반복 XXXXXXX회)
        // main 종료
    }
}
```

**핵심 포인트**: `volatile`이 없으면 워커 스레드가 `running`을 캐시된 값으로만 읽어 무한 루프에 빠질 수 있다. 단, volatile은 가시성만 보장하므로 `count++` 같은 복합 연산에는 D-1/D-2의 도구를 써야 한다.

## E. 동시성 문제 재현

### E-1. 동기화 없는 카운터에서 race condition 재현

```java
public class RaceConditionDemo {
    static int count = 0; // 아무 보호 장치 없는 공유 변수

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                count++; // 읽기 → +1 → 쓰기 (3단계, 원자적이지 않음!)
            }
        };

        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();

        System.out.println("기대값: 200000, 실제: " + count);
        // 기대값: 200000, 실제: 137482  <- 실행마다 다르며, 거의 항상 200000보다 작다
    }
}
```

**핵심 포인트**: 두 스레드가 같은 값을 동시에 읽고 각자 +1 해서 쓰면 증가 하나가 사라진다(lost update). 실행할 때마다 결과가 달라지는 것 자체가 race condition의 증거다. 해결은 D-1(synchronized) 또는 D-2(AtomicInteger).

### E-2. 락 순서가 엇갈리는 데드락 재현과 해결

```java
public class DeadlockDemo {
    static final Object lockA = new Object();
    static final Object lockB = new Object();

    // 주의: 이 프로그램은 데드락으로 영원히 멈출 수 있다 (강제 종료 필요)
    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {               // 1) A를 잡고
                System.out.println("t1: A 획득");
                sleep(100);
                synchronized (lockB) {           // 2) B를 기다림 (t2가 쥐고 있음)
                    System.out.println("t1: B 획득");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {               // 1) B를 잡고
                System.out.println("t2: B 획득");
                sleep(100);
                synchronized (lockA) {           // 2) A를 기다림 (t1이 쥐고 있음)
                    System.out.println("t2: A 획득");
                }
            }
        });

        t1.start(); t2.start();
        // t1: A 획득
        // t2: B 획득
        // ... 이후 서로가 가진 락을 기다리며 영원히 정지 (데드락)
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

해결: **락 획득 순서를 통일**한다. 두 스레드 모두 항상 A → B 순서로 잡게 바꾸면 데드락이 사라진다.

```java
        // t2를 다음처럼 수정: t1과 같은 순서(A → B)로 획득
        Thread t2 = new Thread(() -> {
            synchronized (lockA) {               // t1과 동일하게 A부터!
                System.out.println("t2: A 획득");
                sleep(100);
                synchronized (lockB) {
                    System.out.println("t2: B 획득");
                }
            }
        });
        // t1: A 획득 → t1: B 획득 → t2: A 획득 → t2: B 획득 (순서는 t2가 먼저일 수도 있음)
        // 항상 정상 종료된다
```

**핵심 포인트**: 데드락의 성립 조건 중 "순환 대기"를 끊는 가장 실용적인 방법이 전역 락 순서 통일이다. 락이 여러 개라면 "항상 같은 순서로 잡는다"를 팀 규칙으로 정한다.

### E-3. 타임아웃 있는 락 시도로 무한 대기 방지

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class TryLockDemo {
    static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws InterruptedException {
        // t1이 락을 3초간 점유
        Thread t1 = new Thread(() -> {
            lock.lock();
            try {
                System.out.println("t1: 락 획득, 3초간 작업");
                Thread.sleep(3000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                lock.unlock(); // 락 해제는 반드시 finally에서
            }
        });

        // t2는 최대 1초만 기다리고 포기
        Thread t2 = new Thread(() -> {
            try {
                if (lock.tryLock(1, TimeUnit.SECONDS)) { // 1초 안에 못 잡으면 false
                    try {
                        System.out.println("t2: 락 획득 성공");
                    } finally {
                        lock.unlock();
                    }
                } else {
                    System.out.println("t2: 1초 대기 후 포기 — 무한 대기 없음");
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        t1.start();
        Thread.sleep(100); // t1이 먼저 락을 잡도록 약간 대기
        t2.start();
        t1.join(); t2.join();
        // t1: 락 획득, 3초간 작업
        // t2: 1초 대기 후 포기 — 무한 대기 없음
    }
}
```

**핵심 포인트**: `synchronized`는 락을 잡을 때까지 무한정 기다리지만, `ReentrantLock.tryLock(시간)`은 제한 시간 후 `false`를 반환해 대안 로직(포기/재시도/에러 응답)으로 빠질 수 있다. `unlock()`은 반드시 `finally`에 둔다.

## F. 통합 챌린지

### F-1. 주문 처리 큐 (Producer + Consumer 스레드풀 + 재시도/로그)

```java
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicLong;

public class OrderProcessingDemo {

    // F-2. 최신 문법 적용 1: 주문 데이터는 record로 (불변 + toString 자동)
    record Order(int id, String item, int retryCount) {
        Order retry() { return new Order(id, item, retryCount + 1); }
    }

    enum Result { SUCCESS, RETRYABLE_FAIL, FATAL_FAIL }

    static final int ORDER_COUNT = 20;
    static final int MAX_RETRY = 2;

    // F-3. 메트릭 수집용 카운터
    static final AtomicInteger successCount = new AtomicInteger();
    static final AtomicInteger failCount = new AtomicInteger();
    static final AtomicLong totalLatencyMs = new AtomicLong();

    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Order> queue = new LinkedBlockingQueue<>();
        ExecutorService consumers = Executors.newFixedThreadPool(3);

        // Producer: 주문 생성 스레드
        Thread producer = new Thread(() -> {
            for (int i = 1; i <= ORDER_COUNT; i++) {
                try {
                    queue.put(new Order(i, "상품-" + i, 0)); // 가득 차면 자리 날 때까지 대기
                    System.out.println("[생산] 주문 " + i + " 접수");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }
        });
        producer.start();
        producer.join(); // 데모 단순화: 생산 완료 후 소비 시작 상태 확정

        // Consumer: 스레드풀에서 큐를 비울 때까지 처리
        while (!queue.isEmpty()) {
            Order order = queue.poll();
            if (order == null) break;
            consumers.submit(() -> process(order, queue));
        }
        // 재시도 주문이 큐에 다시 들어올 수 있으므로 잠시 후 잔여분 처리
        consumers.shutdown();
        consumers.awaitTermination(10, TimeUnit.SECONDS);
        drainRetries(queue); // 남은 재시도 주문을 현재 스레드에서 마저 처리

        printMetrics(); // F-3
    }

    static void process(Order order, BlockingQueue<Order> queue) {
        long start = System.currentTimeMillis();
        Result result = doWork(order);
        totalLatencyMs.addAndGet(System.currentTimeMillis() - start);

        // F-2. 최신 문법 적용 2: 처리 결과 분기는 switch 표현식으로
        String log = switch (result) {
            case SUCCESS -> {
                successCount.incrementAndGet();
                yield "[성공] " + order;
            }
            case RETRYABLE_FAIL -> {
                if (order.retryCount() < MAX_RETRY) {
                    queue.offer(order.retry()); // 재시도 큐 재투입
                    yield "[재시도 예약] " + order;
                }
                failCount.incrementAndGet();
                yield "[최종 실패] 재시도 초과: " + order;
            }
            case FATAL_FAIL -> {
                failCount.incrementAndGet();
                yield "[최종 실패] 복구 불가: " + order;
            }
        };
        System.out.println(log);
    }

    /** 실제 처리를 흉내: 80% 성공, 15% 재시도 가능 실패, 5% 복구 불가 실패 */
    static Result doWork(Order order) {
        sleep(ThreadLocalRandom.current().nextInt(10, 50)); // 처리 지연 흉내
        int dice = ThreadLocalRandom.current().nextInt(100);
        if (dice < 80) return Result.SUCCESS;
        if (dice < 95) return Result.RETRYABLE_FAIL;
        return Result.FATAL_FAIL;
    }

    static void drainRetries(BlockingQueue<Order> queue) {
        Order order;
        while ((order = queue.poll()) != null) {
            process(order, queue);
        }
    }

    // F-3. 처리량/실패율/평균지연 메트릭 출력
    static void printMetrics() {
        int total = successCount.get() + failCount.get();
        System.out.println("=== 메트릭 ===");
        System.out.println("처리량: " + total + "건 (성공 " + successCount.get()
                + " / 실패 " + failCount.get() + ")");
        System.out.printf("실패율: %.1f%%%n", failCount.get() * 100.0 / Math.max(total, 1));
        System.out.printf("평균 지연: %.1fms%n", (double) totalLatencyMs.get() / Math.max(total, 1));
        // 예시 출력 (수치는 실행마다 다를 수 있음):
        // === 메트릭 ===
        // 처리량: 20건 (성공 19 / 실패 1)
        // 실패율: 5.0%
        // 평균 지연: 29.3ms
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

**핵심 포인트**: `BlockingQueue`가 생산자-소비자 사이의 완충 지대 역할을 하고, `put/poll`이 대기를 알아서 처리한다. 실패를 "재시도 가능/불가"로 구분하고 재시도 횟수를 주문 데이터에 담아 무한 재시도를 막는 것이 실무 패턴이다.

### F-2. 최신 문법(record/switch 표현식) 적용 포인트

F-1 코드에 이미 적용되어 있다. 리팩터링 전후를 비교하면 다음과 같다.

```java
// 1) record 적용 전: 보일러플레이트 클래스
class Order {
    private final int id;
    private final String item;
    private final int retryCount;
    Order(int id, String item, int retryCount) { this.id = id; this.item = item; this.retryCount = retryCount; }
    int getId() { return id; }
    // ... getter 3개 + toString + equals/hashCode 수십 줄
}

// record 적용 후: 한 줄 + 재시도용 파생 메소드만 추가
record Order(int id, String item, int retryCount) {
    Order retry() { return new Order(id, item, retryCount + 1); }
}
```

```java
// 2) switch 문(기존 습관) 대신 switch 표현식: 결과를 "값"으로 받아 누락 분기를 컴파일러가 검증
String log = switch (result) {
    case SUCCESS -> ...;
    case RETRYABLE_FAIL -> ...;
    case FATAL_FAIL -> ...;
}; // enum 상수가 늘어나면 여기서 컴파일 오류 → 분기 누락 사고 예방
```

**핵심 포인트**: record는 "불변 데이터 + 값 동등성"이라는 의도를, switch 표현식은 "모든 경우를 빠짐없이 값으로 변환한다"는 의도를 코드에 그대로 드러낸다. 짧아지는 것은 부수 효과다.

### F-3. 처리량/실패율/평균지연 메트릭 출력

F-1 코드의 `printMetrics()`가 답안이다. 설계 포인트만 정리하면:

1. **수집은 원자 클래스**: 여러 소비자 스레드가 동시에 갱신하므로 `AtomicInteger`(건수)/`AtomicLong`(누적 지연)을 쓴다. 일반 `int`로 세면 E-1의 race condition으로 수치가 유실된다.
2. **지연 측정**: 처리 직전에 `System.currentTimeMillis()`를 찍고, 완료 후 차이를 누적한다. 평균 = 누적 지연 / 처리 건수.
3. **실패율**: 최종 실패 건수 / 전체 처리 건수. 재시도 후 성공한 건은 실패로 세지 않는다.
4. **0 나누기 방지**: `Math.max(total, 1)`처럼 분모를 보호한다.

```java
// 출력 예시 (수치는 실행마다 다를 수 있음)
// === 메트릭 ===
// 처리량: 20건 (성공 19 / 실패 1)
// 실패율: 5.0%
// 평균 지연: 29.3ms
```

**핵심 포인트**: 동시성 코드의 메트릭은 "수집 자체가 스레드 안전한가"부터 확인해야 한다. 원자 클래스 기반 카운터는 가장 단순하면서도 정확한 수집 도구다.

## 제출 체크리스트 답안 가이드

1. **최신 문법이 가독성을 높였는가**: record는 불변 DTO에(F-1의 `Order`), switch 표현식은 "모든 경우를 값으로 변환"하는 분기에(A-2, F-1) 적용했는지 확인한다. 짧아지기만 하고 의도가 흐려지면(B-2) 명시 타입/기존 문법으로 되돌린다.
2. **공유 자원 접근 규칙**: 공유 가변 상태마다 보호 수단(synchronized/Atomic/volatile/BlockingQueue)을 하나 정해 일관되게 썼는지 확인한다 (D절).
3. **종료/예외/타임아웃 처리**: `shutdown + awaitTermination`(C-2), `join`(C-1), `tryLock(시간)`(E-3), `InterruptedException` 시 인터럽트 상태 복원이 포함됐는지 확인한다.
4. **race condition 재현과 해결 검증**: 동기화 없는 버전에서 기대값과 다른 결과(E-1)를 눈으로 확인한 뒤, synchronized/Atomic 버전(D-1, D-2)에서 항상 기대값이 나오는지 반복 실행으로 검증한다.
